# 📘 Database 모델링의 원칙

> **대상:** 데이터베이스 입문자  
> **목표:** 모델링의 필요성과 핵심 원칙을 이해하고, 올바른 설계 습관을 익힌다

---

## 1. Database 모델링이란?

### 정의

**Database 모델링(Database Modeling)** 은 현실 세계의 데이터를 **구조적으로 표현**하여 DB에 저장하고 활용할 수 있도록 설계하는 과정입니다.

> 💡 한 줄 정의: **"현실을 데이터 구조로 번역하는 작업"**

---

### 왜 필요한가?

모델링이 없을 때 발생하는 문제들을 먼저 살펴봅시다.

| 문제 상황 | 발생 원인 |
|---|---|
| 데이터 중복 | 같은 정보가 여러 곳에 저장됨 |
| 데이터 불일치 | 값이 서로 다르게 저장됨 |
| 쿼리 복잡도 증가 | JOIN이 난잡해짐 |
| 유지보수 어려움 | 구조 변경이 어려워짐 |

> ⚠️ **핵심 메시지:** 잘못된 모델링 = 나중에 모든 것이 고통

---

## 2. 핵심 원칙 5가지

---

### 원칙 1. 현실을 정확히 반영하라

현실에 존재하는 객체(Entity)를 테이블로 만든다.

**현실 세계 → DB 테이블 변환 예시**

| 현실의 객체 | DB 테이블 |
|---|---|
| 고객 | `Customer` |
| 주문 | `Order` |
| 상품 | `Product` |

> 🔑 **핵심 질문:** "이것은 독립된 존재인가?"

---

### 원칙 2. 한 테이블은 하나의 역할만 가져야 한다

테이블은 **하나의 주제**만 담당해야 합니다. (Single Responsibility)

**❌ 잘못된 예 — 두 역할이 섞인 테이블**

```sql
Customer_Order_Table
- customer_name
- order_product_name
- order_date
```

**✅ 올바른 예 — 역할을 분리하고 관계로 연결**

```sql
Customer     -- 고객 정보만 담당
Order        -- 주문 정보만 담당
```

---

### 원칙 3. 중복 데이터를 제거하라 (정규화)

같은 데이터를 여러 번 저장하지 않습니다.

**❌ 잘못된 구조 — 주문마다 고객 정보가 반복됨**

```sql
Order
- customer_name   -- ← 반복!
- customer_address -- ← 반복!
- order_date
```

**✅ 올바른 구조 — customer_id로 연결**

```sql
Customer
- customer_id  (PK)
- name
- address

Order
- order_id     (PK)
- customer_id  (FK)  ← Customer를 참조
- order_date
```

---

### 원칙 4. 관계(Relationship)를 명확히 정의하라

테이블 간의 관계를 명확히 설계해야 합니다.

| 관계 유형 | 설명 | 예시 |
|---|---|---|
| **1 : 1** | 한 개 ↔ 한 개 | 사람 ↔ 여권 |
| **1 : N** | 한 개 ↔ 여러 개 | 고객 ↔ 주문 |
| **N : M** | 여러 개 ↔ 여러 개 | 학생 ↔ 수업 |

**1:N 관계 예시 (가장 중요!)**

```
Customer (1) ──────< Order (N)
고객 1명은 여러 주문이 가능
```

**N:M 관계 — 연관 테이블(Associative table)로 해결**

```sql
-- N:M 관계는 직접 연결 불가 → 연관 테이블 생성
Student(학생) ──── Enrollment(등록) ──── Course(과정)
                   - student_id (FK)
                   - course_id  (FK)
```

---

### 원칙 5. 키(Key)를 명확히 정의하라

| 키 종류 | 설명 |
|---|---|
| **PK (Primary Key)** | 각 행(row)을 고유하게 식별하는 값 |
| **FK (Foreign Key)** | 다른 테이블을 참조하는 값 |

**예시**

```sql
Customer
- customer_id  (PK)  ← "이 고객을 구분하는 값"
- name

Order
- order_id     (PK)  ← "이 주문을 구분하는 값"
- customer_id  (FK)  ← "어느 고객의 주문인지 연결"
```

> 💡 **기억하세요**
> - `PK` = 이 row를 구분하는 값
> - `FK` = 다른 테이블과 연결하는 값

---

## 3. 초보자가 자주 하는 실수

| 실수 유형 | 잘못된 코드 | 문제점 |
|---|---|---|
| **모든 걸 한 테이블에 넣기** | `customer_name`, `product_name`을 같은 테이블에 | 유지보수 불가 |
| **FK 대신 문자열로 연결** | `customer_name = '홍길동'` | 이름 변경 시 전부 수정해야 함 |
| **관계를 설계하지 않음** | 테이블 간 연결 없음 | JOIN이 불가능한 구조 생성 |

---

## 4. 모델링 절차 (실무 흐름)

```
Step 1. 요구사항 분석
        └─ 어떤 데이터를 저장해야 하는가?
           어떤 기능이 필요한가?
           
Step 2. 엔티티 도출
        └─ 고객, 주문, 상품 ...

Step 3. 속성 정의
        └─ Customer: id, name, email ...

Step 4. 관계 정의
        └─ Customer 1 : N Order

Step 5. 키 정의
        └─ PK / FK 설정

Step 6. 정규화
        └─ 중복 제거 및 구조 최적화
```

## 5. 직관적 비유 — 엑셀 vs 잘 설계된 DB

**❌ 엑셀 방식 (잘못된 모델링) — 고객 정보가 반복 저장됨**

| 주문번호 | 고객이름 | 주소 | 상품 |
|---|---|---|---|
| 1 | 홍길동 | 서울 | 노트북 |
| 2 | 홍길동 | 서울 | 마우스 |

**✅ DB 방식 (정상 모델링) — 중복 제거 + 구조화**

**Customer 테이블**

| id | name |
|---|---|
| 1 | 홍길동 |

**Order 테이블**

| id | customer_id | 상품 |
|---|---|---|
| 1 | 1 | 노트북 |
| 2 | 1 | 마우스 |

> 고객 주소가 바뀌어도 `Customer` 테이블 한 곳만 수정하면 됩니다.

## 6. 핵심 요약

반드시 기억할 **5가지 원칙**

| # | 원칙 | 핵심 |
|---|---|---|
| 1 | 현실 반영 | 현실의 객체를 그대로 구조화 |
| 2 | 단일 역할 | 한 테이블 = 한 역할 |
| 3 | 정규화 | 중복 데이터 제거 |
| 4 | 관계 정의 | 1:1 / 1:N / N:M 명확히 |
| 5 | 키 설정 | PK / FK 반드시 설정 |
